### A2. Методы: что нужно уметь объяснить

| Метод | Ключевая идея | Теория, которую нужно знать | Слабое место (пример для защиты) |
|---|---|---|---|
| Rule-based | правила синонимов + Жаккар `|A∩B| / |A∪B|` | множества, коэффициент Жаккара | все слова равны по весу; не знает синонимов вне правил |
| BoW | вектор частот слов + косинус | векторное пространство, `CountVectorizer`, косинусное сходство `a·b / (‖a‖‖b‖)` | частые слова («aitu», «как») доминируют |
| TF-IDF | вес = tf × idf, биграммы, `sublinear_tf` | формула idf в sklearn: `ln((1+n)/(1+df)) + 1`, L2-нормализация, зачем `1 + ln(tf)` | «сколько стоит обучение» → «проживание»: совпадают слова, не смысл |
| Embeddings | нейросеть кодирует смысл фразы в вектор 384 чисел | sentence-transformers, mean pooling, контрастивное обучение на парафразах, почему нормализованные векторы → косинус = скалярное произведение | MiniLM слабее словарных методов на этом наборе; медленнее и тяжелее |
| pg_trgm | доля общих триграмм символов | триграммы (`"аиту"` → `"  а"," аи","аит","иту","ту "`), `similarity` vs `word_similarity`, GIN/GiST индексы | ловит опечатки, но не смысл |
| Стемминг vs лемматизация | Snowball отрезает окончания, pymorphy3 ищет словарную форму | морфология русского | лемматизация дала +0.07…0.08 MRR — почему |

### A3. Метрики и методология

- **Precision@1, Precision@3 (точнее — Hit@k / Success@k)**: был ли правильный ответ на 1-м / в топ-3. На защите честно сказать, что при одном правильном ответе P@k в классическом смысле = Hit@k / k, у нас считается доля запросов с попаданием.
- **MRR** = среднее `1 / ранг первого правильного`; 0, если не попал в топ-3.
- **Порог `min_score`**: компромисс «ответил неправильно» vs «не ответил». Сейчас пороги выбраны вручную — это вопрос, который обязательно зададут (см. C2).
- **Утечка данных (data leakage)**: правила rule-based и словарь синонимов писались, глядя на те же 40 вопросов, на которых метод потом оценивается. Отсюда «baseline победил» — нужен отдельный dev и test (см. B1).
- **Статистическая значимость**: на 40 вопросах разница 0.62 vs 0.60 MRR — это один-два вопроса. Нужны доверительные интервалы (см. C1).

## B. Больше тестовых данных

Сейчас: 40 перефраз, только «положительные» (ответ в FAQ есть), правильный ответ — один (плюс точные дубликаты ответа). Цель: **150–250 вопросов** с разметкой по типам.

### B1. Новый формат `data/test_queries.csv`

```
query,true_question,alt_questions,query_type,split,source
сколько стоит учеба,Какова стоимость обучения в университете?,Сколько стоит обучение в AITU?,synonym,test,manual
скок стоит общага,Сколько стоит проживание в общежитии?,,slang,dev,manual
стоимасть обучения,Какова стоимость обучения в университете?,,typo,test,augmented
где купить билет на концерт,,,out_of_scope,test,manual
```

| Поле | Зачем |
|---|---|
| `alt_questions` | допустимые альтернативные ответы (пересекающиеся записи FAQ, «Контакты AITU» vs «Как связаться с приёмной комиссией?»). Через `;`. Убирает заниженные метрики, о которых написано в PROGRESS §13 |
| `query_type` | разрез метрик по типу запроса (C3) |
| `split` | `dev` — на нём подбираются правила и пороги, `test` — только итоговая оценка. Решает проблему утечки |
| `source` | `manual` / `dataset_paraphrase` / `augmented` / `llm` — честно показать, откуда данные |
| пустой `true_question` | вопрос вне FAQ: правильное поведение — «не нашёл» |

Изменения в коде: `load_test_set` (разбор `alt_questions` в `acceptable`), `test_queries` (колонки `query_type`, `split`, `true_faq_id NULL`), `evaluate_method` (метрики для out-of-scope).

### B2. Откуда взять вопросы

| Источник | Сколько | Как |
|---|---|---|
| Готовые перефразы в датасете (8 групп, 35 вопросов) | ~25 | один вопрос группы — «FAQ», остальные — тестовые. Это **реальные** перефразы, самые ценные |
| Ручные перефразы по категориям | 60–80 | по 5–10 на каждую категорию FAQ (поступление, стоимость, общежитие, гранты, специальности, ЕНТ, магистратура, контакты…). Писать разными способами: синоним, сленг, короткий запрос («грант?»), длинный с лишними словами, порядок слов |
| Вопросы вне FAQ (negatives) | 30–50 | 1) явно чужие темы («погода в Астане»); 2) **близкие, но отсутствующие** («есть ли военная кафедра», «можно ли перевестись из другого вуза» — проверить, что их нет в FAQ). Вторые важнее: на них методы и ошибаются |
| Автоматическая аугментация | ×2–3 к ручным | скрипт `augment.py`: опечатки (перестановка / пропуск буквы), транслит («obshaga»), раскладка, удаление вопросительного знака и заглавных, удаление одного слова. Тип `typo` / `translit`. Не смешивать с ручными в одной метрике |
| Перефразы от LLM | 50–100 | сгенерировать, **вручную проверить каждую**, пометить `source=llm`. Показать метрики отдельно: на LLM-перефразах embeddings обычно сильнее, чем на ручных — это тоже вывод |
| Реальные вопросы из бота | сколько наберётся | попросить 5–10 одногруппников задать боту по 10 вопросов, потом разметить из `requests` правильный ответ. Это **настоящий трафик** — самый сильный аргумент на защите |

## C. Аналитика для защиты

### C1. Надёжность сравнения методов

- **Bootstrap-доверительные интервалы** для P@1 и MRR (1000 перевыборок тестовых вопросов) → таблица «MRR 0.62 [0.51; 0.72]». Если интервалы перекрываются — «разница не доказана», и это честный вывод.
- **Парный тест** между двумя лучшими методами: тест Макнемара по P@1 (на каждом вопросе: оба правы / только A / только B / оба нет) или парный перестановочный тест по reciprocal rank. Данные уже есть в `predictions`.
- **Dev vs test**: метрики rule-based на dev и на test. Если на test просел — это утечка, хороший пункт для обсуждения.

### C2. Порог «не нашёл» — подобрать, а не задать руками

С out-of-scope вопросами можно посчитать для каждого метода и каждого порога от 0 до 1:

- **answered accuracy** — доля правильных среди ответов, данных выше порога;
- **coverage** — доля in-scope вопросов, на которые метод ответил;
- **false answer rate** — на скольких out-of-scope вопросах метод уверенно ответил.

График «coverage vs accuracy» (кривая для каждого метода) + выбор порога на dev по F1 / максимуму `accuracy` при `coverage ≥ 0.8` → проверка на test. Плюс гистограмма оценок: правильные ответы vs неправильные vs out-of-scope — видно, разделимы ли они вообще (у embeddings оценки «плотные», 0.4–0.9, у TF-IDF — разброс шире).

### C3. Разрезы метрик

- по `query_type` (синоним / сленг / опечатка / короткий / out-of-scope) — тепловая карта «метод × тип», главный слайд: **каждый метод силён в своём** (pg_trgm — опечатки, rule-based — сленг из правил, embeddings — синонимы);
- по категориям FAQ — для этого закрыть пункт «свести 422 метки в 8–10 категорий» (`data/category_map.json`);
- **confusion matrix по категориям**: в какую категорию уходит ответ при ошибке (стоимость ↔ общежитие и т. п.);
- по длине запроса (1–2 слова vs 3–5 vs 6+).

### C4. Анализ ошибок

- таблица из 10–15 характерных ошибок с типами: «совпали слова, не смысл», «правильный ответ — дубликат с другим текстом», «вопрос вне FAQ, но метод уверен», «опечатка»;
- запрос `test_errors` уже есть — дополнить колонкой типа ошибки (ручная разметка);
- **oracle**: доля вопросов, где хотя бы один метод прав на 1-м месте — верхняя граница для комбинации методов.

### C5. Ресурсы

- время поиска: не только среднее, а **медиана, p95, max** (по `method_runs.time_ms`) — boxplot по методам;
- время подготовки и память — уже есть в `methods`;
- график «качество (MRR) vs время поиска» (scatter, размер точки — память) — компромисс на одном слайде.

### C6. Улучшения методов (дают выводы, а не только цифры)

| Эксперимент | Ожидание | Сложность |
|---|---|---|
| Лемматизация в боте по умолчанию | +0.07 MRR, уже доказано тестом | 1 строка |
| `intfloat/multilingual-e5-small` или `LaBSE` вместо MiniLM | embeddings выходят вперёд (для e5 нужны префиксы `query:` / `passage:`) | небольшая — новый класс в `methods/` |
| Индексировать вопрос **+ ответ** (а не только вопрос) | выше recall на редких формулировках | параметр в `fit` |
| **Гибрид**: `α·TF-IDF + (1−α)·embeddings` или Reciprocal Rank Fusion | лучше каждого по отдельности; α подбирать на dev | новый класс, ~20 строк |
| Удалить near-duplicates из FAQ (`near_duplicate_questions`) | меньше «ложных ошибок» | SQL + перезапуск |
| `TfidfVectorizer(analyzer="char_wb", ngram_range=(3,5))` | устойчивость к опечаткам как у pg_trgm | 1 параметр |

### C7. Где показать

- `analysis.ipynb` (уже в планах): EDA данных + все графики C1–C5 — основной артефакт для отчёта;
- вкладка дашборда «Оценка»: таблица `runs` с интервалами, тепловая карта по типам, кривая порогов;
- 2–3 новых SQL-запроса в `queries.sql`: метрики по `query_type` (GROUP BY + FILTER), перцентили времени (`percentile_cont`), coverage / accuracy при пороге (CTE + CASE).
