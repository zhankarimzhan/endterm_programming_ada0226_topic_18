# Как работают методы поиска

Все пять методов решают одну задачу: **посчитать сходство** вопроса пользователя с каждым из 556 вопросов FAQ. Бот берёт вопрос с наибольшим сходством и отдаёт его ответ; если сходство ниже порога метода — отвечает «не нашёл». Отличаются методы только тем, **как считается сходство**.

Код: каждый метод — отдельный файл в `methods/`, общий интерфейс — `methods/base.py` (`fit()` строит индекс по вопросам FAQ, `scores()` возвращает сходство запроса с каждым вопросом, `search()` — топ-k с ответами).

Пример везде один: запрос **«сколько стоит обучение в аиту»**.

---

## Общая предобработка (`preprocessing.py`)

Используется в rule-based, BoW и TF-IDF:

1. нижний регистр, `ё` → `е`;
2. разбивка на слова: `сколько`, `стоит`, `обучение`, `в`, `аиту`;
3. удаление стоп-слов (`в`, `и`, `на`…) — но вопросительные слова («как», «сколько», «где») **сохраняются**: в FAQ они несут смысл вопроса;
4. **стемминг** (Snowball) — отрезание окончаний: `обучение` → `обучен`. Так «обучение», «обучения», «обучением» становятся одним словом. Альтернатива — лемматизация (pymorphy3), переключается параметром `mode`.

Результат: `[сколько, стоит, обучен, аиту]`.

---

## 1. Rule-based (baseline) — `methods/rule_based.py`

**Идея:** простые правила + подсчёт общих слов.

1. **Правила замены** приводят разные написания к одному виду: `аиту` / `astana it university` → `aitu`, `общага` → `общежитие`, `цена` / `оплата` → `стоимость`, `универ` / `вуз` → `университет`.
2. Предобработка → каждый вопрос становится **множеством слов**.
3. **Сходство = коэффициент Жаккара:**
   ```
   общих слов / всего разных слов в обоих вопросах
   ```
   Запрос `{сколько, стоит, обучен, aitu}` и FAQ «Сколько стоит обучение?» `{сколько, стоит, обучен}`: общих 3, всего разных 4 → **0.75**.

- **Порог:** 0.15
- **Плюсы:** понятен, очень быстр, правила ловят сленг («общага»).
- **Минусы:** не знает синонимов вне правил; все слова одинаково важны («сколько» весит как «обучение»).

---

## 2. Bag of Words — `methods/bow.py`

**Идея:** вопрос → вектор, где каждая позиция — сколько раз встретилось слово.

1. Словарь строится по всем вопросам FAQ (`CountVectorizer`).
2. Каждый вопрос → вектор длиной в весь словарь: `[сколько: 1, стоит: 1, обучен: 1, общежит: 0, …]`.
3. **Сходство = косинус угла** между вектором запроса и вектором вопроса FAQ (1 — одинаковый набор слов, 0 — ни одного общего).

- **Порог:** 0.3
- **Плюсы:** стандартный, быстрый, учитывает повторы слов.
- **Минусы:** все слова равноценны — «сколько стоит **обучение**» и «сколько стоит **проживание**» совпадают на 2 из 3 слов, бот их путает.

---

## 3. TF-IDF — `methods/tfidf.py`

**Идея:** как BoW, но **редкие слова важнее частых**.

- **TF** (term frequency) — насколько часто слово в самом вопросе.
- **IDF** (inverse document frequency) — насколько слово **редкое** во всём FAQ. «aitu» есть почти в каждом вопросе → низкий вес; «общежитие» — в нескольких → высокий.
- **Вес слова = TF × IDF.**

Дополнительно: **биграммы** (пары слов подряд: «сколько стоит», «проходной балл») и `sublinear_tf` (повтор слова не раздувает вес). Сходство — косинус между векторами, как в BoW.

- **Порог:** 0.3
- **Плюсы:** решают важные слова; сейчас это **метод по умолчанию в боте**.
- **Минусы:** не понимает смысл и синонимы — «стоимость обучения» и «сколько стоит учиться» для него разные слова.

---

## 4. Embeddings — `methods/embeddings.py`

**Идея:** готовая нейросеть переводит **смысл** фразы в вектор из 384 чисел; близкие по смыслу фразы → близкие векторы.

1. Модель `paraphrase-multilingual-MiniLM-L12-v2` (sentence-transformers) **уже обучена** на миллионах пар перефраз. Мы её **не обучаем**, только применяем.
2. При запуске все 556 вопросов FAQ один раз переводятся в векторы.
3. Запрос → вектор, **сходство = косинус**.
4. Предобработка не нужна — модель работает с исходным текстом.

Пример: «сколько стоит обучение» → «**Какова стоимость обучения в университете?**» (0.76) — общих слов почти нет, но смысл совпал. Единственный метод, который справился с этим запросом.

- **Порог:** 0.5 (у embeddings оценки в целом выше)
- **Плюсы:** понимает синонимы и перефразы, работает на разных языках.
- **Минусы:** медленнее; модель ~470 МБ, загрузка ~7 с; не видно, «почему» выбран ответ; иногда цепляется за мусор (так нашлась строка `questions` в данных).

---

## 5. pg_trgm (дополнительный SQL-метод) — `methods/pg_trgm.py`

**Идея:** сравнение по **кусочкам из трёх букв**, считается прямо в PostgreSQL.

1. Слова режутся на триграммы: `аиту` → `"  а"`, `" аи"`, `"аит"`, `"иту"`, `"ту "`.
2. SQL-функция `word_similarity`: **какая доля триграмм запроса нашлась в каком-то фрагменте вопроса** FAQ.
3. Длинный вопрос в FAQ не штрафуется за лишние слова.

- **Порог:** 0.3
- **Плюсы:** устойчив к опечаткам («поступить» / «поступление» делят много триграмм); всё делает база.
- **Минусы:** не понимает смысл, не знает синонимов; AITU и аиту для него разные строки (разные алфавиты).

---

## Сводка

| Метод | Что сравнивает | Синонимы | Опечатки | Скорость |
|---|---|---|---|---|
| Rule-based | общие слова + ручные правила | только из правил | ✗ | ⚡ очень быстро |
| BoW | количество слов | ✗ | ✗ | ⚡ |
| TF-IDF | слова с учётом редкости | ✗ | ✗ | ⚡ |
| Embeddings | **смысл** фразы | ✓ | частично | медленнее |
| pg_trgm | кусочки из 3 букв | ✗ | ✓ | ⚡ (в базе) |

Какой метод на самом деле лучше, покажут **метрики на тестовых вопросах** (Precision@k, MRR) — следующий шаг проекта (`evaluation.py`).
