# Ход работы над проектом

**Тема 18. University FAQ Retrieval Chatbot** — итоговый проект по дисциплине «Programming for Data Analysis and Database».

Репозиторий: https://github.com/zhankarimzhan/endterm_programming_ada0226_topic_18

## Суть проекта

Чат-бот для абитуриентов Astana IT University. Пользователь пишет вопрос своими словами, бот находит в базе FAQ самый похожий вопрос и выдаёт готовый ответ. Бот ничего не генерирует — он **ищет** среди готовых пар «вопрос — ответ».

Главный вопрос проекта: какой способ поиска лучше находит нужный ответ — простое совпадение слов (baseline), BoW / TF-IDF или смысловые эмбеддинги, и чем приходится платить за качество (время, память).

## Данные

- Датасет: [AITU Admissions Guide Dataset](https://huggingface.co/datasets/Arailym-tleubayeva/AITUAdmissionsGuideDataset) (Hugging Face, файл `QA_addmissionAitu.csv`).
- Колонки: `questions`, `answers`, `classes`. Язык — русский.
- Статья, на которой основан датасет (для ссылки в отчёте):
  A. Tleubayeva et al., "Systemic approach to optimizing natural language processing technologies in Astana IT University's admissions process," IEEE SIST 2024, pp. 520–525, doi: 10.1109/SIST61555.2024.10629481.
- Тема 18 входит в список исключений по объёму данных (не нужно 500 тыс. строк).

| Проблема | Значение |
|---|---|
| Строк в исходных данных | 608 |
| Точные дубликаты (вопрос + ответ) | 29 |

| Строки без «?» (описания курсов, а не вопросы) | 47 |

### Что полезного есть в данных

- **8 групп, 35 вопросов** с разными формулировками и одним ответом — готовые перефразы для тестового набора (~25 тестовых вопросов).
- Колонка `classes` — после сведения в 8–10 категорий пригодится для confusion matrix и SQL-запросов по категориям.

Вычисляется, а не хранится (`sql/init/03_views.sql`):
- `v_method_answers` — ответ каждого метода: найден ли (оценка ≥ порога метода);
- `v_unanswered` — вопросы, на которые ни один метод не нашёл ответа, с ближайшим кандидатом;
- `v_test_hits` — последний прогон каждого метода на каждом тестовом вопросе: место первого верного ответа, уверенная ошибка (неверный ответ выше порога).

SQL-скрипты: `sql/init/01_schema.sql` (таблицы), `02_search.sql` (pg_trgm), `03_views.sql` (представления); миграции старой базы — `sql/migrations/` (001 нормализация, 002 режим test, 003 наборы тестовых вопросов, 004 отказ от отзывов; все выполнены).

### 5. Первый метод поиска — `pg_trgm` (средствами PostgreSQL)
Сходство по триграммам символов: устойчиво к опечаткам и написанию «аиту» / «AITU».

| Запрос | Найдено | |
|---|---|---|
| как поступить в аиту | Что нужно сдать чтобы поступить в АИТУ? (0.81) | ✓ |
| какие предметы ент для информационной безопасности | Какие предметы для Информационной безопасности? (0.92) | ✓ |
| сколько стоит обучение | Сколько стоит проживание в общежитии? (0.59) | ✗ |

Третий пример — слабое место символьного сходства (совпадает «сколько стоит», а смысл другой). Это пример для анализа ошибок; такие случаи должны исправлять эмбеддинги.

### 6. Пять методов поиска — каждый в своём файле (`methods/`)

Все методы реализуют общий интерфейс `SimilarityMethod` (`methods/base.py`): `fit()` строит индекс по вопросам FAQ, `scores()` возвращает сходство запроса с каждым вопросом, `search()` — топ-k с ответами.

| Файл | Метод | Как работает | Предобработка | Порог |
|---|---|---|---|---|
| `methods/rule_based.py` | **Rule-based (baseline)** | правила замены синонимов (аиту → aitu, общага → общежитие, цена → стоимость…) + доля общих слов (Жаккар) | стемминг | 0.15 |
| `methods/bow.py` | **Bag of Words** | `CountVectorizer` + косинусное сходство | стемминг | 0.3 |
| `methods/tfidf.py` | **TF-IDF** | `TfidfVectorizer` (слова + биграммы, sublinear tf) + косинусное сходство | стемминг | 0.3 |
| `methods/embeddings.py` | **Embeddings** | `paraphrase-multilingual-MiniLM-L12-v2` (sentence-transformers), косинусное сходство векторов | нет (исходный текст) | 0.5 |
| `methods/pg_trgm.py` | **pg_trgm** (доп. метод) | `word_similarity` по триграммам в PostgreSQL | нижний регистр | 0.3 |

`preprocessing/` — общая предобработка: токенизация, стоп-слова NLTK (вопросительные слова «как», «где», «сколько» сохраняются), стемминг Snowball и лемматизация pymorphy3 (переключается параметром `mode`). Данные NLTK хранятся в `nltk_data/` проекта: NLTK 3.10 не читает каталоги, доступные на запись другим пользователям.

`search/runner.py` — загружает FAQ из базы, готовит все методы (`build_methods`), регистрирует их в таблице `methods` и пишет историю в `chat_log` с указанием метода.

Первое сравнение на трёх запросах (лучший ответ каждого метода):

| Запрос | Rule-based | BoW | TF-IDF | Embeddings | pg_trgm |
|---|---|---|---|---|---|
| как поступить в аиту | ✓ «Как поступить в AITU…» | ✓ | ✓ | ≈ «Что нужно сдать чтобы поступить в АИТУ?» | ≈ то же |
| сколько стоит обучение | ✗ проживание | ✗ проживание | ✗ проживание | ✓ «Какова стоимость обучения в университете?» | ✗ проживание |
| есть ли общага | ✓ «Есть ли у вас общежитие?» (правило) | ✗ ничего | ✗ ничего | ✗ (мусорная строка — удалена) | ✓ «Есть ли общежитие в AITU?» |

Каждый метод ошибается по-своему — поэтому нужен тестовый набор и метрики (P@k, MRR), а не 3 примера.

### 8. Вопросы без ответа
- Отзывы 👍/👎 убраны (миграция 004): качество методов меряется только на тестовых вопросах с известным правильным ответом — отзывы были редкими и смещёнными, а правило «👍 одному ответу = 👎 остальным методам» ошибалось на равноценных ответах.
- Вопрос без ответа вычисляется представлением `v_unanswered`: ни один метод не прошёл порог. Хранится ближайший кандидат.
- Это список того, чего не хватает в FAQ (вкладка «Предложения» в дашборде).

### 9. Статистика `/stats` (для всех пользователей)
Считается SQL-запросами (`analytics/stats.py`): всего вопросов, найдено / не найдено, по каждому методу — % найденных, среднее сходство, время, память, MRR на тестовых вопросах и место (`RANK()`), метрики на обоих тестовых наборах, частые вопросы без ответа.

### 10. Дашборд — мини-приложение Telegram

Сейчас и в браузере, и в Telegram (`/app`) открывается один и тот же HTML-дашборд (`web/dashboard.html` поверх API): `run.sh` поднимает быстрый туннель cloudflared на порт API и передаёт его HTTPS-адрес боту как `WEBAPP_URL`. Внутри Telegram страница берёт цвета темы пользователя. Ниже — описание первой версии на Streamlit (`dashboard.py`), она сохранена, но не запускается.
Закрывает требование 7 («мини-дашборд на Streamlit с фильтрами»). Вкладки:
- **Статистика** — показатели, таблица и график по методам, вопросы по дням;
- **Запросы** — все вопросы с фильтрами (режим, метод, найден / не найден, поиск по тексту), выданный ответ;
- **Совпадения** — распределение сходства по методам, самые частые ответы, проверка вопроса всеми 5 методами сразу;
- **Предложения** — вопросы без ответа, сгруппированные по тексту, что предложил бот, кнопка «отметить как обработанные».

Открытие в Telegram: `/app` → «📊 Открыть дашборд»; после `/start` или `/app` у пользователя появляется кнопка «Дашборд» рядом с полем ввода (кнопку по умолчанию для всех чатов Telegram для мини-приложений не применяет, поэтому она ставится в чате пользователя).

- Telegram открывает мини-приложения только по HTTPS, поэтому дашборд (порт 8501) публикуется через **быстрый туннель cloudflared** (`~/.local/bin/cloudflared`, запускается вручную).
- Доступ к дашборду — по ключу `DASHBOARD_KEY` из `.env`: бот сам подставляет его в ссылку, без ключа страница не открывается.
- Адрес быстрого туннеля меняется при каждом перезапуске → его нужно вписать в `WEBAPP_URL` в `.env` и перезапустить бота. Текущий адрес можно узнать: `curl -s http://127.0.0.1:20241/quicktunnel`.
- Внимание: в дашборде видны тексты вопросов всех пользователей (без имён и id).

### 11. Режим сравнения методов (по умолчанию в боте) — требование 9

### 12. SQL-аналитика — требование 10 (`queries.sql`)

13 запросов к нормализованной схеме; выполняются `analytics/queries_runner.py` (результаты → pandas → `results/sql/*.csv`) и во вкладке «SQL» дашборда.

| Ключ | Что считает | Конструкции |
|---|---|---|
| `labels_with_many_questions` | метки датасета с ≥ 5 вопросами | GROUP BY, HAVING |
| `frequent_terms` | самые распространённые стеммы (df ≥ 20) | JOIN, GROUP BY, HAVING |
| `tfidf_keywords` | топ-3 ключевых слова по TF-IDF для каждой крупной метки | CTE, подзапрос, ROW_NUMBER |
| `near_duplicate_questions` | почти одинаковые вопросы FAQ (Жаккар ≥ 0.8) | self-JOIN, CTE, HAVING |
| `method_leaderboard` | места методов по качеству и скорости | CTE, RANK × 2 |
| `method_agreement` | как часто два метода дают одинаковый ответ | self-JOIN, CTE |
| `unique_wins` | тестовые вопросы, на которые верно ответил только один метод | CTE, HAVING, STRING_AGG |
| `missed_by_tfidf` | тестовые вопросы: embeddings ответил верно, TF-IDF — нет | EXISTS, NOT EXISTS |
| `quality_by_type` | P@1, MRR и уверенные ошибки по типам формулировок | представление, RANK OVER PARTITION |
| `magnet_answers` | ответы, которые методы чаще всего ошибочно выдают первыми на тестах | JOIN, HAVING, STRING_AGG |
| `daily_activity` | вопросы по дням, накопительный итог, изменение | CTE, SUM OVER, LAG |
| `test_errors` | анализ ошибок на тестовых вопросах: сколько методов ошиблись и что выдали | представление (DISTINCT ON), JOIN, HAVING, STRING_AGG |
| `unanswered_gaps` | приоритет вопросов без ответа | представление, DENSE_RANK, LATERAL (в представлении) |

Находка: `near_duplicate_questions` нашёл в FAQ дубликаты, пропущенные очисткой (например, «Где находится Astana IT University AITU (аиту)?» и «Где находится Astana IT University (AITU / аиту)?») — пункт для аудита данных.

### 13. Тестовые вопросы и оценка методов — первичный запуск (`init_project.py`)

`data/test_queries.csv` — 40 вопросов из FAQ, перефразированных «как спросил бы абитуриент» (сокращения, «аиту», «общага», разговорные формы). Правильный ответ задан текстом вопроса FAQ; ответ метода засчитывается, если **текст ответа** совпадает с правильным (дубликаты вопроса с тем же ответом тоже верны).

`init_project.py` — отдельный скрипт, запускается **один раз** после `docker-compose up -d`:
1. загружает FAQ и строит обратный индекс (если база пуста);
2. готовит методы;
3. `analytics/evaluation.py`: прогоняет тестовые вопросы через все методы **и варианты с лемматизацией** → `test_queries`, `runs` (P@1, P@3, MRR, время, память), `predictions` (топ-3 каждого метода) — отдельно для каждого набора: `base` (`data/test_queries.csv`) и `paraphrases` (`data/paraphrases.csv`, 64 формулировки 10 вопросов с типом: сленг, синоним, опечатка, транслит, английский, зеркальные).

Повторный запуск ничего не дублирует; `--force` — пересчитать.

Результаты (40 вопросов, топ-3):

| Метод | Предобработка | P@1 | P@3 | MRR | Поиск |
|---|---|---|---|---|---|
| Rule-based (baseline) | лемматизация | **0.53** | **0.75** | **0.62** | 0.6 мс |
| TF-IDF | лемматизация | 0.50 | 0.72 | 0.60 | 1.2 мс |
| Bag of Words | лемматизация | 0.53 | 0.68 | 0.59 | 1.1 мс |
| Rule-based (baseline) | стемминг | 0.47 | 0.62 | 0.54 | 0.4 мс |
| Bag of Words | стемминг | 0.47 | 0.60 | 0.54 | 0.8 мс |
| TF-IDF | стемминг | 0.42 | 0.65 | 0.53 | 0.9 мс |
| Embeddings (MiniLM) | — | 0.38 | 0.57 | 0.46 | 12.4 мс |
| pg_trgm | нижний регистр | 0.35 | 0.55 | 0.43 | 12.0 мс |

Выводы (предварительные):
- **лемматизация лучше стемминга** у всех трёх словарных методов (MRR +0.07…0.08);
- **embeddings MiniLM хуже словарных методов** на этих перефразах и в 10–20 раз медленнее, занимает 450 МБ — кандидат на замену более сильной многоязычной моделью (например, `intfloat/multilingual-e5-small` или LaBSE);
- **метрики — нижняя оценка**: запрос `test_errors` показывает, что во многих «ошибках» метод нашёл другой подходящий по смыслу вопрос FAQ с иным текстом ответа («как связаться с приемкой» → «Как связаться с приемной комиссией?» вместо «Контакты AITU»). В FAQ много пересекающихся записей с разными ответами — это проблема данных, а не только методов.

## Как запустить

```bash
./run.sh                      # всё одной командой: база, зависимости, данные, API + дашборд, бот (--no-bot — без бота)

# или по шагам:
[ -f .env ] || cp .env.example .env   # только если .env ещё нет; вписать пароль базы, TELEGRAM_BOT_TOKEN, DASHBOARD_KEY
docker-compose up -d          # поднять PostgreSQL
python -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python init_project.py  # первичный запуск: FAQ, индекс, оценка на тестовых вопросах (один раз)
.venv/bin/python -m search.runner    # проверить поиск всеми методами
.venv/bin/python -m analytics.stats  # статистика в консоли

# каждое в своём терминале:
.venv/bin/streamlit run dashboard.py                                   # старый дашборд Streamlit, http://localhost:8501 (не обязателен)
.venv/bin/uvicorn api.app:app --port 8000                             # API + HTML-дашборд, http://localhost:8000/?key=DASHBOARD_KEY
~/.local/bin/cloudflared tunnel --no-autoupdate --url http://localhost:8501   # HTTPS-адрес → WEBAPP_URL в .env (или :8000 для HTML-дашборда)
.venv/bin/python bot.py                                                # Telegram-бот (запускать после WEBAPP_URL)
```

Если схему меняли: `docker-compose down -v && docker-compose up -d` (скрипты из `sql/init/` выполняются только на пустой базе). Старую базу (с `chat_log`) обновить без потери данных:
```bash
docker exec -i faq-postgres psql -v ON_ERROR_STOP=1 -U faq -d faq_db < sql/migrations/001_normalize.sql
docker exec -i faq-postgres psql -v ON_ERROR_STOP=1 -U faq -d faq_db < sql/init/03_views.sql
.venv/bin/python -m data_prep.term_index
```
SQL-аналитика: `.venv/bin/python -m analytics.queries_runner`.

⚠️ `data_prep/storage.py` (`load_to_db(replace=True)`) при перезаписи делает `TRUNCATE faq CASCADE` — вместе с FAQ очищаются кандидаты, отзывы и обратный индекс (индекс перестраивается автоматически).
